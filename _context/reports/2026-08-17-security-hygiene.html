Content-Security-Policy set

Security headers

No Content-Security-Policy — the main defense against injected/3rd-party scripts is missing.

How to fixA Content-Security-Policy is your main defense against XSS — it controls which scripts and styles are allowed to run.
  1. Add the Content-Security-Policy header using the starter config below.
  2. Ship it as Content-Security-Policy-Report-Only first and watch the violation reports.
  3. Widen the script/style/connect sources to the ones your site actually uses, then switch from Report-Only to enforcing.
Config — Vercel
// vercel.json → "headers": [{ "source": "/(.*)", "headers": [ … ] }]
{ "key": "Content-Security-Policy", "value": "default-src 'self'; img-src 'self' data: https:; style-src 'self' 'unsafe-inline'; script-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'" }
Starter policy — widen the script/style/connect sources to the ones your site really uses, or it'll block them. Test in report-only first.
MEDIUM

Clickjacking protection

Security headers

No X-Frame-Options and no CSP frame-ancestors — the site can be framed for clickjacking.

How to fixWithout it, your pages can be embedded in an attacker's invisible iframe for clickjacking.
  1. Add X-Frame-Options: DENY (config below), or `frame-ancestors 'none'` in your CSP if you already send one.
  2. If you embed your own pages, use SAMEORIGIN / an explicit `frame-ancestors` allowlist instead.
  3. Re-scan.
Config — Vercel
// vercel.json → "headers": [{ "source": "/(.*)", "headers": [ … ] }]
{ "key": "X-Frame-Options", "value": "DENY" }

MIME-sniffing disabled

Security headers

No X-Content-Type-Options: nosniff header.

How to fixWithout nosniff, a browser may guess a response's type and execute something you served as plain data.
  1. Add X-Content-Type-Options: nosniff (config below).
  2. Make sure your responses send correct Content-Type headers so nothing breaks.
  3. Re-scan.
Config — Vercel
// vercel.json → "headers": [{ "source": "/(.*)", "headers": [ … ] }]
{ "key": "X-Content-Type-Options", "value": "nosniff" }

Security headers

No Permissions-Policy header to lock down camera/mic/geolocation access.

How to fixWithout it, embedded third-party code can quietly request camera, microphone, or geolocation.
  1. Add a Permissions-Policy header that denies the features you don't use (config below).

ADVISORY

DMARC is enforcing (p=quarantine) — confirm every sending tool is authorized

Email authentication

With an enforcing DMARC policy, mail from any service that sends as this domain but isn't listed in SPF (or DKIM-signed) is quarantined or bounced. DNS can't see which tools you use, so this check stays visible until you confirm it yourself, then mark it complete.

How to fix
  1. List every tool that sends mail as "@your-domain": Google Workspace, lead-nurture (Instantly, Smartlead, Lemlist), CRM/marketing (HubSpot, Mailchimp, Customer.io), helpdesks (Intercom, Zendesk, Front), transactional senders (Resend, SendGrid, Postmark, Supabase Auth, Stripe receipts), and form/booking notifications.
  2. From each tool, send a test message to a Gmail address you control.
  3. In Gmail, open the message → ⋮ menu → "Show original." Look for SPF, DKIM, and DMARC — each should end in PASS. Any FAIL / SOFTFAIL means that tool isn't covered.
  4. For any tool that didn't pass: open its domain settings, copy the SPF include and DKIM record it gives you, and publish them at your DNS provider. Re-test until all three say PASS.
  5. Strongly recommended: move cold / bulk outreach to a SEPARATE sending domain so its reputation can't drag down signup verifications and password resets on your primary domain.
  6. When every sender passes, mark this complete. It will keep showing until you do — and if you add a new tool later, come back and re-verify.
